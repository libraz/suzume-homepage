# 仕組み

## なぜこんなに小さいのか？

Suzume の WebAssembly バイナリは、内蔵辞書を含めて gzip 後に約 <WasmSize /> です。従来の辞書ベースの解析器が数十 MB 級の辞書を必要とすることが多い中、どのようにバイナリを小さく保っているのでしょうか。

### 簡潔な答え

| | IPADIC 系辞書を使う MeCab | Suzume |
|---|---------------------------|--------|
| 語彙 | 形態情報を持つ広範な単語リストを読み込む | 選択した単語と例外を保存する |
| 接続 | 事前計算済みの接続コスト行列を読み込む | コンパクトな規則から接続を計算する |
| 辞書にない語 | 文字種ごとの未知語定義を使う | パターンから候補を生成する |

このドキュメントで MeCab との比較に使う正確な構成は、[比較条件](/ja/docs/mecab-comparison#比較条件)に記載しています。どちらがどの用途に向くかは[使い分けの指針](#when-to-use-which)で説明します。

### 3 つの柱

<DiagramPillars />

::: info トークン化とは？
テキストを意味単位（トークン）に分割し、品詞を特定することです。日本語では「東京に行く」のような連続テキストを「東京 / に / 行く」に分割します。
:::

## 1. 最小限の辞書

辞書ベースの解析器は、網羅的な単語リストを保存しています。

```
# MeCab辞書エントリ（簡略化）
東京,名詞,固有名詞,地域,*,*,*,東京,トウキョウ,トーキョー,0/3,C1
```

Suzume は高頻度の機能語、助詞、助動詞、例外語を中心に保存します。多くの内容語は、すべての表層形を辞書に持つのではなく、文字種パターンや文法規則から候補を作ります。

| カテゴリ | 辞書ベースの解析器 | Suzume |
|----------|--------------------|--------|
| 機能語 | 辞書に収録 | コンパクトなエントリと文法規則 |
| 動詞・形容詞 | 多数の表層形・活用形エントリ | 活用規則と選択的な例外 |
| 一般名詞・固有名詞 | 広範な語彙を収録 | 文字種パターンの候補とコンパクトな辞書 |
| ドメイン固有語 | 辞書パッケージまたはカスタマイズ | 実行時ユーザー辞書 |

## 2. パターン認識 {#pattern-recognition}

すべての単語を保存する代わりに、パターンを認識します。

<DiagramPattern />

::: info なぜこれが機能するのか
日本語の文字種と活用語尾は、候補を作る手掛かりになります。Suzume はその手掛かりを辞書エントリや前後の接続スコアと組み合わせます。パターンに一致しただけで、最終的な品詞や境界が決まるわけではありません。
:::

手元のテキストで試してみてください。プレイグラウンドは各トークンの出どころを表示するので、辞書から引いたトークンとパターンから生成したトークン（[未知語](/ja/docs/glossary#unknown-word)）を見分けられます。

<TokenizerPlayground />

## 3. 動的な接続スコアリング

IPADIC などの MeCab 辞書には、事前計算済みの接続コスト行列が含まれます。

```
# どの単語がどの単語の後に来れるか？（簡略化）
名詞 → 助詞: コスト 100
名詞 → 動詞: コスト 500
助詞 → 名詞: コスト 50
...数百万の組み合わせ
```

Suzume はコンパクトな規則で接続スコアを動的に計算します。

<DiagramScoring />

## 判定の一貫性

Suzume は文字種・活用・接続の共通規則から境界と品詞を決めるため、同じ構文はどこに現れても同じように解析されます。たとえば `じゃ` は、`本じゃない`、`本じゃなかった`、`本じゃな` のいずれでも原形 `だ` の `AUX` になります。これは規則の性質であって、Suzume の分割だけが正しいという主張ではありません。具体例は[コピュラ否定](/ja/docs/mecab-grammar#copula-negation)と[使役受身](/ja/docs/mecab-grammar#使役受身)を、規則の限界は[制約](/ja/docs/mecab-comparison#制約)を参照してください。

## 技術的な詳細

::: info ラティスとは？
テキストを分割するすべての可能な方法を表すグラフ構造です。ラティスを通る各パスが 1 つのトークン化候補になります。「すもも」の場合、「すもも」（李）や「す/もも」（酢＋桃）などのパスがあります。
:::

::: info Viterbi アルゴリズムとは？
ラティスを通る最適なパスを見つける動的計画法のアルゴリズムです。すべての組み合わせを評価する代わりに、途中の計算を再利用して最適な分割を効率よく見つけます。
:::

### 解析パイプライン

<DiagramPipeline />

パイプラインは常にこの順で動きます。`スカイツリー` のような[未知語](/ja/docs/glossary#unknown-word)はパターンの経路を通ります。カタカナの連続から名詞候補を作り、その候補はラティス内でほかのすべての候補と競合し、Viterbi のスコアが最もよい場合だけ残ります。

オプションはパイプラインそのものではなく、その入力と出力を変えます。対象は[正規化](/ja/docs/analysis-modes#normalization)、[解析モードと複合語の結合](/ja/docs/analysis-modes#modes)、辞書の読み込み、スコアラー設定、そして JavaScript ではインスタンスごとに独立した WASM ランタイムを使うかどうかです。全項目は [API リファレンス](/ja/docs/api) を参照してください。

### 動詞活用

Suzume は各活用形を個別の語彙エントリとして用意するのではなく、共通の活用規則から規則的な活用形を導出します。一部の辞書エントリは、辞書のコンパイル時または読み込み時に活用形へ展開されます。実行時の展開については[ユーザー辞書](/ja/docs/user-dictionary)を参照してください。

```
原形: 食べる
├── 食べ + ない → 否定
├── 食べ + ます → 丁寧
├── 食べ + た → 過去
├── 食べ + て → て形
└── 食べれ + ば → 仮定
```

## 使い分けの指針 {#when-to-use-which}

Suzume は、検索や表示のためのコンパクトなトークン化を目的に作っており、同じコアがブラウザ、エッジやサーバーのランタイム、Python、Go、C/C++ で動きます。MeCab のような辞書ベースの解析器は目的の異なる道具で、その辞書の語彙カバレッジや詳細な品詞体系が要件のときに選びます。両者の出力は相互に置き換えることを意図していないため、MeCab との一致率は Suzume の評価指標ではありません。

| 要件 | 選ぶもの | 理由 |
|------|----------|------|
| サーバーなしでブラウザやクライアント側でトークン化したい | Suzume | コンパクトな辞書を WASM バイナリに内蔵している（gzip 後に約 <WasmSize />） |
| 入力中のテキストをその場でトークン化したい | Suzume | ネットワークの往復がない |
| 検索インデックスやタグ抽出 | Suzume | 複合語を 1 トークンに保てる。[`search` モード](/ja/docs/analysis-modes#modes)では結合もする |
| どの辞書にも載っていない語 | Suzume | 辞書エントリのない文字列もパターンから候補を作れる |
| ブラウザ、サーバー、Python、Go、C/C++ で同じトークナイザーを使いたい | Suzume | すべてのバインディングが 1 つのコアを使う |
| 特定の MeCab 辞書やコーパスとの互換性 | MeCab | その辞書の境界と品詞体系を保つ |
| 複合語の内部で辞書が定める境界（`東京都庁前`） | MeCab | 境界は選択した辞書から決まる。Suzume では[ユーザー辞書](/ja/docs/user-dictionary)に登録する |
| 読みと詳細な品詞階層 | MeCab | 辞書がそれらを提供する。Suzume の[品詞](/ja/docs/glossary#pos)体系はより粗い |

同じ入力での具体的な違いは [MeCab との違い](/ja/docs/mecab-comparison) を参照してください。
